# PesaTrack Repository Audit — 2026-10-04

Audited branch baseline: `main@f865f544ad8b9e5f84155df3651b200238d54ec4`

## Executive result

The project is substantially healthier than the older handoff implied.

The previously unfinished Message Lab parser-draft work is **already complete and extended**. Main now includes:
- evidence queue;
- semantic labeling;
- parser readiness;
- review-only parser drafts;
- implementation review;
- implementation work packets;
- Inspector handoff;
- sanitized resolution archive;
- resolved-coverage regression checking;
- semantic-agreement guard before retirement.

There is no active “price check” feature/task in repository history. That phrase appears to have been unrelated speech-to-text rather than a missing PesaTrack requirement.

## What is working well

### Financial intelligence
The core direction is correct:
- provider-agnostic interpretation;
- canonical records;
- explicit pending/failed suppression;
- debt semantics;
- mirror/duplicate correlation;
- local learning;
- identity graph;
- Message Pack fixtures;
- real-device/regression corpus;
- history reprocessing;
- evidence-driven long-tail coverage.

The code no longer looks like the old provider-by-provider `if/else` design PesaTrack was trying to escape.

### Privacy
- local SQLite source of truth;
- app backup disabled in manifest;
- cleartext traffic disabled;
- remote enrichment is optional;
- worker rejects likely sensitive descriptors;
- raw SMS is not part of the remote enrichment contract.

### Threading
The main heavy user flows inspected (Home, Activity, Data Health, Smart Onboarding) push substantial local work to `Dispatchers.IO`.
Remote enrichment is performed from WorkManager.

### CI
Current main Android CI is green and publishes the rolling debug APK.

## Problems found

### P0 — misleading live preview surfaces
Community and Goals were reachable from production navigation despite not being real financial features.

Examples:
- Community explicitly says it is a preview/not live.
- Goals contains hard-coded values such as Couch/PS5/Emergency Fund/Land and historical 2024/2025 dates.

Action in this audit:
- quarantine these routes from live navigation;
- keep files temporarily so design work is not destroyed;
- document that they are not product scope.

### P0 — documentation drift
`PROJECT_CONTEXT.md` is useful as a chronological handoff but has grown beyond 4,000 lines.
It is not a good first source for “what PesaTrack is”.

Action:
- rewrite README around current truth;
- add a stable Product Charter;
- add this audit;
- keep PROJECT_CONTEXT as historical detail, not product definition.

### P1 — giant files / concentration risk
Largest high-risk files include approximately:
- `ActivityScreen.kt`: 4.7k lines;
- `DataHealthScreen.kt`: 4.7k lines;
- `SmartOnboardingSetupScreen.kt`: 4.6k lines;
- `TransactionStore.kt`: 3.7k lines;
- `DebtStore.kt`: 2.8k lines;
- `MessageLabStore.kt`: 2.2k lines;
- `IdentityGraphStore.kt`: 2.1k lines;
- `FinancialMessageIngestionCoordinator.kt`: 2.0k lines;
- `FinancialCandidateExtractor.kt`: 1.9k lines;
- `FinancialRelationshipResolver.kt`: 1.7k lines;
- `PesaTrackDatabase.kt`: 1.5k lines.

This is now a correctness risk because state, SQL, migration, policy and UI can become difficult to isolate.

Required direction:
- no substantial new feature work inside these files until they are progressively decomposed;
- split by responsibility, not by arbitrary line count.

### P1 — no Android instrumentation tests
There are many JVM tests but currently no `app/src/androidTest` Kotlin tests.

Risk:
- navigation, permission flows, SQLite upgrade behavior and Compose interactions are not exercised on Android runtime in CI.

Recommendation:
Start with a small high-value suite:
1. fresh install -> onboarding -> Home;
2. existing install schema migration -> launch;
3. historical import permission denied/granted;
4. Activity -> transaction detail;
5. Data Health smoke test.

### P1 — database migration path is unproven
Schema is currently v31 and `onUpgrade` contains sequential migrations.
The logic looks deliberate, but there is no automated migration matrix.

Required:
- create representative old-version databases;
- exercise upgrades to v31;
- assert tables/columns/triggers and preserved ledger rows.

### P1 — CI lacked lint
Action in this audit:
- add `:app:lintDebug` to the existing Android CI gate.

### P1 — stale open PRs
The audit found four old PRs still open even though main had advanced far beyond them:
- #43 Move Fuliza message meaning into generic debt interpretation;

### P1 — public enrichment endpoint needs abuse controls
The Android client correctly does not carry a reusable secret for the Worker, so the public resolve endpoint can be called by anyone who discovers it.

Current source has descriptor privacy validation and bounded provider timeouts, but no application-level rate limiting or quota enforcement.

Required deployment hardening:
- enforce Cloudflare-side rate limiting / abuse controls on `/v1/entity/resolve`;
- monitor Worker/provider request volume and failure rates;
- keep provider credentials server-side;
- do not “solve” this by embedding a secret API key in the APK;
- consider caching safe repeated commercial descriptors server-side only if the privacy contract remains intact.

### P2 — developer diagnostics leaked into user attention
Home and Activity's user-facing Needs Attention counts included active Message Lab unsupported parser shapes.

That mixed developer parser backlog with user-resolvable financial review work.

Action completed:
- Home and Activity no longer count or surface Message Lab unsupported shapes as user review work;
- transaction/duplicate/relationship/identity review remains user attention;
- parser evidence remains in Data Health, which is still reachable from More.

### P2 — settings implied unavailable features
Backup/restore and PIN/biometric lock were displayed as ordinary Settings rows even though they are not implemented.

Action:
- make the copy explicitly state these are planned/not active.

### P2 — superseded onboarding source remains
`InitialMoneySetupScreen.kt` and `PermissionSetupScreen.kt` remain in source but are not part of the current NavHost.

Recommendation:
- keep them quarantined through one green cleanup release;
- then delete them if no tests/references require them.

## What should happen next

Do not start a new numbered “phase”.

Priority order:
1. merge this product-boundary/documentation cleanup if CI is green;
2. add Android migration + smoke instrumentation tests;
3. decompose the highest-risk giant files;
4. continue parser expansion only from real Message Lab evidence;
5. measure real review burden on-device and improve the dominant source of uncertainty.

## Hard stop rules

Do not:
- add more preview features;
- reconnect Community/Goals merely because UI exists;
- invent provider templates without evidence;
- auto-promote Message Lab drafts into production;
- let optional enrichment write accounting truth;
- add another broad feature before migration/testing and file-size debt begin to improve.
